# Decisions and open questions

A short record of choices we made and why, so neither of us has to reconstruct the reasoning later, and so a coding agent reading the repo does not undo a decision on purpose. Add an entry when you decide something that is not obvious from the code.

## Decided

**Name: agentGuard, kept knowingly.** There is a name collision and we are choosing to live with it, so the reasoning belongs on the record.

`AgentGuard: Learning Execution Guardrails from Anomalous Coding-Agent Trajectories` (arXiv:2609.16287, September 2026) has our exact name, in our exact subfield, and is evaluated on Claude Code. Also in the neighbourhood: `AgentGuardian` (arXiv:2601.10440), `bashguard` and `sh-guard` as open-source tools, and `ShellSieve` as one of the papers we cite. We checked `agentShield` as an alternative and it is worse — there is an `AgentShield` paper on tool-using agent security (arXiv:2605.11026, May 2026), four GitHub repositories, and packages on both npm and PyPI. The whole "agent" plus guard-word namespace is saturated; roughly fifteen collisions turned up without looking hard.

Consequences we accept by keeping the name. The paper must distinguish itself from arXiv:2609.16287 explicitly and early, which is easy because the mechanisms are opposites: they learn rules from failure traces and inject them into the agent's context with no runtime enforcement, while we enforce at the dispatch boundary. Searching for our work will surface theirs. And if this is ever released as a package, the name on PyPI will have to differ from the name in the paper.

If we do rename later, the name appears in only six places across five files — `README.md` twice, `AGENTS.md`, `compiler/grammar.md`, `pyproject.toml`, and this entry — plus the GitHub repository name, the local folder and both of our git remotes. Candidates that avoid the saturated namespace entirely, by naming the metaphor rather than the function: Portcullis, Barbican, Lintel, Cordon, Parley. None is verified.

**Classifier: zero-shot NLI, not Jev.** Jev (TypeSafe AI) is a hosted classifier and needs an API key, which makes the project non-reproducible for anyone without an account. An open-source NLI model runs locally. Do not reintroduce an API-key dependency.

Correction to how we argue this. "No API key" does **not** distinguish us from CARE: its README configures the judge through an OpenAI-compatible endpoint and demonstrates a locally served model, so CARE can run entirely offline too. The defensible version of the claim is **no LLM anywhere in the decision path** — our classifier is a small discriminative model that can only tighten a verdict, where CARE's judge is a 30-billion-parameter generative model that can flip a deny to an allow. CARE's own RedCode-gen numbers, where the full system left more realised harm than the static profile alone, are the evidence that this distinction matters. Use that argument, not the API-key one.

**The repo is public.** See the publication rules in `README.md` and `AGENTS.md`. The practical consequence is that the bypass corpus is generic shell technique, never a working attack on a named product.

**Two licences: MIT for code, CC BY 4.0 for data.** A public repository with no licence grants nobody any rights, which defeats the point of publishing an artifact alongside a paper. MIT is the permissive default in this area and is what CARE uses, so it maximises the chance anyone reuses our compiler; Apache-2.0 would add an explicit patent grant if we ever wanted that. The corpora under `bench/` are licensed separately because we expect them to be reused on their own and because data and code want different terms — attribution matters more than warranty disclaimers. Entries derived from MITRE ATT&CK, GTFOBins, RedCode or CARE's published data carry those sources' terms and record their provenance. `SECURITY.md` holds the matching disclosure policy, including the rule that a bypass we find in someone else's tool goes to its maintainers before it goes into our repository.

**No parser generators in the core.** The lexer and parser are written by hand, because this is a compilers course project and that is the part being assessed. Tree-sitter or `bash -n` may be used in tests as an independent oracle to compare our parse against.

**The grammar is a documented subset of POSIX Issue 8, section 2.** We use the standard's own token names and productions rather than inventing our own, so our accepted language is checkable against a specification. Every existing tool in this space borrows a parser instead (CARE uses `bashlex`, bashguard uses `tree-sitter-bash`, others use regex), and none states what language it accepts; see `docs/related-work.md`. The accepted subset and the explicit rejected-construct list are in `compiler/grammar.md`.

**Anything outside the grammar is a denial, not a parse failure.** This is what makes the from-scratch grammar a security property rather than a limitation, and it is why unspecified POSIX behaviour is also rejected: a divergence between our reading and the real shell's is exactly a bypass.

**Words carry quoting provenance; we never expand.** A word is a list of parts, each tagged with how it was written (literal, single-quoted, `$'...'`, parameter expansion, command substitution, glob, and so on), and a word is resolved only when every part is statically known. The prior tools normalize and decode to produce a string to match; normalization is lossy, and refusing to decide is not. This is the direct response to the GuardFall quoting bypasses.

**The gate is session-aware.** We track the working directory, resolved variable assignments, and the history of denied effects. CARE states that its mediation is stateless and per-command, which is why a sequence like `cd ~/Desktop` followed by `cat notes.txt` is invisible to it. Session state is also what makes retry detection possible, which is the survey's RG3 "verifier tax" and the gap we are aiming at.

**Verdicts form a lattice and only ever tighten.** `ALLOW < ESCALATE < DENY`; every stage may raise a verdict and none may lower it. CARE reports that its LLM judge made realised harm *worse* than its static profile by flipping warn cases to allow, which is the empirical argument for the rule already in `AGENTS.md` that the classifier may only tighten.

**Here-documents with a quoted delimiter are accepted.** `cat <<'EOF'` makes the body a pure literal, and agents use the form constantly to write files and commit messages, so rejecting it would have cost a large share of ordinary commands for no security benefit. The original reason for rejecting it — that the body is attacker-controlled text of arbitrary length — applies equally to a single-quoted string, which we accept. An unquoted delimiter stays refused, because its body is expanded and therefore not statically known. `compiler/grammar.md` section 3.2 carries the corrected reasoning.

**Package layout: top-level `compiler/`, `classifier/`, `gate/`.** The design review recommended moving to `src/agentguard/` with an editable install and called the root `conftest.py` a workaround, which it is. We kept the flat layout anyway, because it is what `AGENTS.md` and `TEAM.md` already document and both of us are reading those. Revisit if the import path becomes a nuisance; moving is mechanical while the code is small.

**Development environment: a venv inside the repo.** `.venv/` is already gitignored. Python 3.12, with `ruff`, `pytest` and `hypothesis` from `requirements-dev.txt`. `hypothesis` was added for the fail-closed property test, which asserts that `LexError` is the only exception the lexer can raise for any input — the property the gate's fail-closed behaviour rests on.

**The argv oracle, and its exception to the never-execute rule.** Comparing our word values against the arguments bash really passes is the only way to test the lexer against reality, and it needs the shell. `AGENTS.md` now carries the narrow, bounded exception that permits it: generated words only, `printf` only, container only, test modules only. Its first run checked twelve words, agreed on eleven, and found a genuine bug — bash keeps the backslash on an unrecognised `$'...'` escape, so `$'\8'` is `\8` and not `8`. One note for whoever extends it: on Windows, pass the script to bash over stdin, because `subprocess` rebuilds an argv list using MS C runtime quoting rules that rewrite backslashes and corrupt the very inputs under test.

## Deferred

**CI guard script.** The hard rules in `AGENTS.md` (the compiler never executes what it analyzes, no committed secrets or data, corpus entries are data not scripts) are prose only; nothing enforces them. The plan is a Python script in `.github/scripts/` run as a CI step, using the `ast` module to reject `eval`, `exec`, `subprocess` and friends in `compiler/` and `classifier/` while exempting `gate/`, whose sandboxed executor legitimately needs them. Deferred until there is code for it to check.

## Open

**Arithmetic expansion runs code stored in variables.** Found while writing the parser, and it belongs to the effect analysis rather than to the grammar. `$((x))` evaluates the *contents* of `x` as an arithmetic expression, and a subscript inside that expression is expanded, so after `x='a[$(cmd)]'` the word `$((x))` runs `cmd` — verified on bash 5.3.15 with `printf`. The parser already refuses `((...))` as a command and refuses a `$(` written directly inside `$((...))`, but it cannot refuse `$((x))` without refusing all arithmetic, because whether `x` holds a payload is session state, not syntax. The assignment that plants the payload is a single-quoted literal with no effects, so a per-command check passes both halves. Two options for 1b: treat any `ARITH_EXP` part that names a variable as an `INTERPRET` effect, which R3 denies; or let it through only when every variable it names is tracked and its value contains no `$`, `` ` `` or `[`. The first is simpler and costs little, since arithmetic in agent commands is rare.

**Variables change in more ways than assignment words.** The session tracks variables set by `ASSIGNMENT_WORD` (`docs/policy-rules.md` §4), and the AST records exactly those. But `${x:=value}` assigns as a side effect of expansion, and `unset`, `read`, `export`, `declare`, `local`, `printf -v`, `mapfile` and `getopts` all change variables as commands. If any of these runs while the tracker believes it still knows `x`, the next `cat $x/file` is resolved against a stale value — a soundness hole in the session state, the part of the design we claim as a contribution. For 1b: any of these should invalidate the variables it names, making them `UNKNOWN` for the rest of the session, and when the names cannot be determined, invalidate every tracked variable. The knowledge table entries for those builtins are where this belongs.

**What does a rejection tell the agent?** A detailed reason ("this would delete files outside the workspace") helps a legitimate retry but teaches the agent where the boundary is, so it can probe around it. A generic refusal does the opposite. This is gate H1 in `gate/hypotheses.md`, to be answered with a measurement rather than a guess.

**Which NLI model.** Piece 2a. Needs to be open-weight, small enough to run on a laptop in the command path, and good enough on the (rejected, next command) task. Record the choice and the latency here once measured.

**Resolution has three values, not two: `KNOWN`, `BOUNDED(dir)`, `UNKNOWN(reason)`.** Adopted, replacing the `RESOLVED`/`UNRESOLVED` pair. This was the open question at the end of `docs/policy-rules.md` and it had to be settled before `compiler/types.py` was written, because the field is the first thing in that file and rule R2 turns on it.

The argument that decided it: **the policy never needs a filename, it needs a region.** Every clause in R4 is a zone test, and a zone is a property of a directory prefix. Two values threw the region away and so collapsed `rm *`, `rm -rf build` and `find . -type f -delete` into one category with no correct treatment — denying it rejects three commands agents run constantly, which is the axis the field is judged on, since over-refusal is the limitation the AgentGuard paper names as its own and a 0.91% false-positive rate is CARE's headline claim; allowing it permits `find / -delete`. Keeping the bound separates them: bounded-by-`workspace/build` is allowed, bounded-by-`/` is denied, and `rm $(cat list)` is `UNKNOWN` and denied by R2.

Two consequences had to be specified rather than left implied. A `BOUNDED(dir)` target covers a subtree, so **its zone is the join of every zone that subtree contains**, not the zone of `dir` itself — otherwise `BOUNDED(~)` reads as `HOME` while containing `~/.ssh`, and `grep -r password ~` is allowed. And containment is **textual, not symlink-aware**, which is now a named residual risk in `docs/threat-model.md` rather than an unstated assumption.

Allowing destruction inside the workspace is not a concession: `docs/threat-model.md` already lists it among the things we do not defend against, since the agent exists to change the workspace. Three-valued resolution is what makes the code match the claim we had already published.

**Canonical emission quotes every known word, and writes known text from its value.** The emitter in `compiler/emit.py` throws away how the agent spelled each known part of a word and writes the value afresh in single quotes, so `a\ b`, `"a b"` and `$'a\x20b'` all become `'a b'`. Inside single quotes nothing is special except the closing quote, which shrinks what has to be right from our whole lexer to one quoting rule. That is the real argument for canonical emission, and the report should make it in these terms.

We considered quoting only where needed, as `shlex.quote` does, so that `ls -la` stays readable, and chose to quote everything. Speed was the worry, and we measured it rather than guessing: quoting 100 words takes 9.3 µs when everything is quoted against 20.3 µs when each word is checked first, and `bash -n` takes 120.8 ms against 119.6 ms on the two outputs, where an empty command takes 120.3 ms — the whole cost is starting the shell. A first bash measurement showed a threefold gap that disappeared under warm-up and alternation, a cold-cache effect. With speed off the table, quoting only where needed costs a second set of rules that must be right — a safe-character list, plus exceptions for `=` and reserved words in command position — to buy readability in a string that bash reads and no person does. The agent is shown its own command, not ours, and `Script.src` keeps it.

Writing the emitter surfaced its own traps, each now handled where it arises and each a case where the obvious output means something else to bash. `( (ls) )` emitted without inner spaces is `((ls))`, which is arithmetic; a substitution opening with a subshell needs a space too, or `$( (ls) )` becomes `$((ls))`. The character after a tilde must stay unquoted, because `~'/x'` is not expanded while `~/'x'` is. A quoted empty string has to survive, because `''$e` with `e` empty is one argument and `${e}` alone is none. And here-document bodies follow the next newline wherever it falls, so the emitter queues them on the line rather than on the command, and refuses the one case where bash's choice of body would be ambiguous.

It also found two bugs in our own front end, which is the clearest evidence for the design. The argv oracle refused every arithmetic expansion, because the parser's check for a substitution hidden inside an expansion matched the `$((` that opens arithmetic itself. And comparing tilde forms against bash showed the lexer marking a tilde after any `=`, where bash requires the word to be shaped like an assignment, and reading `~"$(id)"` as the user name `"$`, which hid the start of a command substitution inside the tilde. Both are fixed with regression tests. The second shows the emitter doing its job even before the fix: whenever our reading and bash's differ, executing our own output makes bash do what we analysed.

**The command parser fails fast; the policy DSL recovers.** Two error models in one project, each chosen for its input, and the contrast is worth a section of the report.

`parse` raises `ParseError(code, message, pos)` on the first construct it refuses, structurally identical to `LexError`, and a Hypothesis property test asserts that `ParseError` is the only exception escaping it for any token list the lexer can produce. The gate then has two failure paths, both DENY with a cited `Diag`. Three codes are already reserved for it in `compiler/syntax.py`: `UNSUPPORTED_CONSTRUCT`, `UNEXPECTED_TOKEN`, `MALFORMED_ASSIGNMENT`.

Four reasons, in the order they convinced us. An AST that failed validation must not be constructible: if `parse` returned a `Script` beside an error list, some caller would eventually walk it without checking, and that caller would be analysing a command we had already refused — one forgotten `if` away from a security bug, where an exception makes the bad state unrepresentable. Second, now that the parser recurses into `$(...)`, an inner failure propagates through an exception for free, whereas collected diagnostics must be merged at every recursive call site and the failure mode of forgetting is silent. Third, the consumer is a policy engine asking one yes-or-no question, not a developer iterating on a message. Fourth, recovery works by fabricating a plausible parse of the region it rejected, which for us means analysing a command nobody wrote.

Precedent is on this side for single-unit inputs: `json.loads` raises on the first problem, Postgres reports one syntax error with a position and abandons the query, and our own target shell does the same — verified on bash 5.3.15, a file with two independent syntax errors on separate lines produces exactly one message and exit status 2. Real language compilers collect and recover instead, and so do the course texts, because their input is a long file and their user is a person in a slow build cycle. Neither condition holds for one command line.

So error recovery goes where it belongs, in the policy DSL's compiler. That input is a genuine source file of many rules, written and edited by us, where independent mistakes really coexist and the author really iterates, and nothing unsafe follows from a partial parse because a policy file that does not fully compile is not loaded. Panic-mode recovery synchronising on rule boundaries is correct there. If the course rubric awards marks for multi-error reporting, that is where we earn them, and the justification for not doing it in the command parser is itself the better answer.

**Command substitution is one token and a nested AST, not one opaque word.** The two questions are separate and POSIX answers them differently. Lexically, `$(...)` stays inside the word token with its characters unmodified, because the standard performs no substitutions during token recognition — so `echo $(date)` is one word token, and our lexer is right as written. Structurally, the inside is a shell program and must be parsed as one: POSIX requires the tokenizing rules to be reapplied recursively to find the matching `)`, and says embedded expansions and quoting inside the substitution are processed recursively. Our lexer already does that recursive *scan* — `_scan_cmd_subst` skips quoted sections and nested parens and records the maximum depth — it simply throws the inside away, keeping the raw text and the depth. The parser will instead hand the captured text back to itself and store the resulting `Script` on the `CMD_SUBST` part.

Every tool in the field borrows a parser that does recurse: bashlex builds a `commandsubstitution` node holding the inner parse under `command`, tree-sitter-bash nests `command` nodes inside `command_substitution`, and `mvdan/sh` holds statements inside its `CmdSubst`. What the guards then do is discard that structure at the rule layer — the common bashlex idiom is a visitor returning `False` to stop descending into the substitution, and CARE reduces the whole construct to two scores, 0.30 for a plain substitution and 0.60 for nesting at depth two or more. So the honest statement for the paper is not that the prior work cannot see inside a substitution; it is that the parsers see inside and the policies decline to look. That is a narrower claim and a checkable one.

The reason we need the structure is that two of our own rules are unimplementable without it. R3 permits an interpreter handoff only when the inline code parses and passes policy recursively, which requires a parse of the inline code. R7 denies a substitution in command-name position, which requires knowing what the substitution would produce there. Without recursion both collapse to "deny every substitution", which is a defensible fail-closed position but costs us the analysis that distinguishes us from a denylist.

**The canonical emitter belongs to 1a.** Until now it was described in `docs/related-work.md` and `docs/threat-model.md` as a design property and assigned to nobody, so it would have been built by neither of us. The design review placed it with the gate (3a); we are putting it in the front end (1a) instead, because it is the inverse of the parser and the round-trip property — parse, emit, re-parse, same AST — is a parser test rather than a gate test. Both pieces are Youssef's either way, so the only thing this changes is which area's `hypotheses.md` records its results. Needs Younes's agreement only in that he is the reviewer.

**Two shared type files instead of one.** `docs/interfaces.md` proposes splitting the contract: `compiler/syntax.py` for what the front end produces (tokens, words, AST nodes, diagnostics), written by Youssef and reviewed by Younes, and `compiler/types.py` for what the middle end produces (`Effect`, `Resolution`, `Zone`, `Verdict`, `Decision`, `SessionState`), written by Younes and reviewed by Youssef. The reason is that one shared file makes every change by either of us a change to the other's file, so the "reviewed by the other member" rule degrades into noise; two files with one author and one reviewer each keep it meaningful. This is what the code has already done — `syntax.py` exists and `types.py` does not — so the decision is really whether to ratify it. Needs Younes's agreement.

**Who maps sandbox observations to effects.** The workaround-success metric compares predicted effects with what the sandbox observed, so one side has to convert filesystem and network observations into `Effect` records. `docs/interfaces.md` S8 proposes the executor does it, being the only piece that knows how its sandbox reports changes. If both sides assume the other converts, the headline number of the paper is uncomputable.

**Who writes the policy language's front end.** By area the policy DSL is Younes's, since it is part of 1b; by skill it is Youssef's, having just written a lexer. `docs/interfaces.md` S9 suggests Younes designs the language and writes its evaluator while Youssef writes its lexer and parser, making it a second deliberate pairing point. Undecided.

**Policy language shape.** What a rule over effects actually looks like, and whether it is YAML or a small DSL we parse ourselves. To be agreed together before `compiler/policy.py` is written.
